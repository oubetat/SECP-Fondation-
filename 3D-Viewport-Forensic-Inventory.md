# SECP-3D-VIEWPORT-FORENSIC-INVENTORY-001
## Comprehensive Forensic Inventory of 3D Viewports and Specialized Visualizations

---

### Executive Summary

A repository-wide forensic audit of all 3D visualization paths, rendering engines, WebGL/WebGPU/Three.js canvases, and specialized visualizers across SECP Industrial OS v2 was conducted in strict accordance with the **SECP-3D-VIEWPORT-FORENSIC-INVENTORY-001** directive.

The audit revealed that 3D rendering and graphic visualization across the platform is partitioned into three distinct tiers:
1. **Primary Interactive 3D WebGL Viewport (`CadViewport3D`)**: The persistent CAD canvas rendered at the root level (`App.tsx`). It features dynamic geometry sourcing: rendering canonical B-Rep meshes when `activeSolid.mesh` is generated by `DocumentEvaluator`, while dynamically falling back to procedural Three.js assemblies (`buildRealisticV6Engine`, `buildSolidWorksBallValve`) when in demo/template modes.
2. **Isolated Prototype 3D Viewport (`Professional3DViewportPanel`)**: A standalone Three.js testbed panel mounted exclusively on `PATCH-276`. It operates completely disconnected from `canonicalDocument`, using hardcoded demo engine block geometry to demonstrate selection, gizmo manipulation, section cutting, PMI, and GD&T features.
3. **Specialized 2D Canvas & SVG Domain Visualizers**: Domain-specific mathematical and kinematic plotters (e.g., `GearEngineeringWorkspace`, `NoiseFilteringWorkbenchPanel`, `AssemblyWorkspace`, `ThreeAxisCamWorkspace`) that render custom 2D canvas graphs and SVG vector overlays independently of the 3D WebGL pipeline.

### 1. Detailed Viewport Forensic Profiles

#### Profile 1: Primary CAD Viewport (`CadViewport3D.tsx`)
* **Component / File**: `/src/components/CadViewport3D.tsx` (1,215 lines)
* **Workbench / Tab Using It**: Mounted at top level in `/src/App.tsx` (lines 1458–1500) across standard engineering workbenches (`V6-ENGINE`, `PATCH-003`, `PATCH-004`, `PATCH-005`, `PATCH-006`, `PATCH-007`, `PATCH-008`, `PATCH-011`, `PATCH-045`, etc.).
* **Rendering Technology**: Three.js WebGL (`THREE.WebGLRenderer`, `THREE.PerspectiveCamera`, `OrbitControls`, `THREE.Group`, `THREE.MeshStandardMaterial`, `THREE.BufferGeometry`, `THREE.EdgesGeometry`).
* **Geometry Source**:
  * *Canonical Mode*: `activeSolid.mesh` (Float32Array vertices, normals, and index buffers evaluated from `DocumentEvaluator.evaluate(canonicalDocument)`).
  * *Assembly Mode*: `assemblyComponents` bounding boxes (`THREE.BoxGeometry`) displaced by `AssemblyEngine.getExplodedPositions`.
  * *Demo / Procedural Mode*: Procedural V6 engine (`buildRealisticV6Engine`) or industrial ball valve/faucet (`buildSolidWorksBallValve`) in `CadIndustrialModels.ts`.
* **EngineeringDocument Source**: Indirectly linked via `activeSolid` and `assemblyComponents` props managed by `App.tsx`.
* **B-Rep Source**: Reads `activeSolid` (`dimensions`, `type`, `mesh`, `colorHex`, `id`, `name`).
* **Topology Source**: Top-level entity identification (`userData = { id: activeSolid.id, name: activeSolid.name }`). Individual face/edge topological sub-entities are not rendered as distinct pickable meshes unless generated in `activeSolid.mesh`.
* **Selection Source**: Raycaster ray intersection on top-level meshes triggers `onSelectComponent(name)`.
* **Transform Source**: Evaluator matrices, `explodedPositions[comp.id]`, and real-time kinematic rotation angles for crankshaft/pistons.
* **Visibility Source**: `comp.visible` flag on assembly items and component layer toggles.
* **Local Geometry State**: Manages local Three.js `sceneRef`, `meshesGroupRef`, `engineRefs`, and `valveRefs`.
* **Local Engineering State**: Internal animation tickers (`internalEngineSimActive`, `internalEngineSpeed`, `angleRef`, `internalValveAngle`).
* **Creates Own Geometry**: **YES** (Constructs Three.js geometries for primitives, fallback procedural engines, and exploded view boxes).
* **Reads `canonicalDocument`**: Indirectly through `activeSolid` and `assemblyComponents`.
* **Calls `DocumentEvaluator`**: **NO** (Consumes pre-evaluated solid from `App.tsx`).
* **Separate Rendering / Geometry Engine**: Three.js WebGL scene graph.
* **Fallback / Mock Geometry**: **YES** (Procedural V6 Engine, SolidWorks Ball Valve, Gooseneck Faucet, Box fallback).
* **Can Diverge from `canonicalDocument`**: **YES** (When `activeProjectType` is `V6_ENGINE` or `BALL_VALVE`, or when `activeSolid` is null, it renders standalone procedural models).
* **Survives Tab Switching**: **YES** (Remains mounted in the persistent upper region of `App.tsx` during standard tab transitions).
* **Classification**: **SPECIALIZED_HYBRID_VIEWPORT** (Canonical evaluator mesh when available; standalone procedural simulator in demo mode).

### 3. Final Forensic Invariant Findings

1. **True 3D WebGL Viewports in Repository**: Exactly **two** Three.js WebGL implementations exist (`CadViewport3D` and `Professional3DViewportPanel`).
2. **Canonical Coupling Reality**:
   * `CadViewport3D` is dynamically coupled to `canonicalDocument` via `activeSolid.mesh` when evaluated solids exist, but maintains independent procedural demo routines when unpopulated.
   * `Professional3DViewportPanel` is entirely decoupled from `canonicalDocument` and functions as a self-contained mock assembly testbed.
3. **2D Canvas Proliferation**: 8+ specialized workbenches utilize raw HTML5 2D canvas drawing contexts to render domain calculations directly from mathematical formulas rather than querying the central CAD kernel.
4. **Tab Switching Survival**: Only `CadViewport3D` survives tab transitions because it is anchored in the root layout of `App.tsx`. All other specialized visualizers unmount and lose their ephemeral visual state when navigating away.
